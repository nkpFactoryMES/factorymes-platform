# 서비스 저장소 분리 Before / After

측정: 2026-11-18, 읽기 전용 구조 검사. Before는 Claude가 보관한 01:11 스냅샷이며,
현재 원본 폴더를 다시 측정해 과거 수치를 바꾸지 않았다.
After는 13:45에 갱신한 11개 저장소 합계다. 소요 시간·캐시 적중률·운영 배포는 측정하지 않았다.

## 왜 저장소를 나누었나

기존에도 프로세스와 HTTP/JWT 경계는 분리되어 있었다. 문제는 런타임보다 빌드 경계였다.
하나의 Dockerfile이 전체 소스를 먼저 복사하고 솔루션을 restore하므로,
한 서비스만 바꾸어도 여러 이미지의 빌드 입력이 함께 변경되었다.
공유 소스와 검증 도구의 ProjectReference도 다른 서비스 소스를 요구했다.

프로세스를 다시 만드는 대신 기존 서비스의 책임과 동작을 유지하면서 저장소·패키지·이미지의
빌드 입력을 분리했다. 업무 도메인별 Backend 분해나 데이터베이스 분리는 이번 범위가 아니다.

## 같은 범위를 비교한 결과

| 항목 | Before 01:11 | After 13:45 |
|---|---:|---:|
| 전체 .NET 프로젝트 | 17 (솔루션 13 + 별도 검증 4) | 17 (11개 저장소 합계) |
| 자체 이미지 빌드 대상 | 10 | 10개 Dockerfile |
| Dockerfile | 1 | 10 |
| 다른 저장소 소스 ProjectReference | 저장소 분리 전에는 해당 경계 없음 | 0 |
| 명시적 Compile의 저장소 밖 소스 포함 | 과거 수치 미측정 | 0 |
| 남은 ProjectReference | 공유 라이브러리·검증 대상 서비스 포함 | Web → Web.Client 1개, 같은 저장소 |
| 사내 패키지 참조 버전 | 소스 ProjectReference 중심 | 모두 정확 범위 [1.0.0] |
| Oracle 업무 데이터 소유 | Backend 32개 테이블 | 기존 Backend 소유 유지 |

After의 17개는 XML로 csproj를 파싱한 실제 목록이다. 패키지 참조도 여러 줄 XML을 처리했다.
Before의 원본 스크립트는 정규식과 비어 있지 않은 소스 줄 수를 사용했다.
따라서 이번에는 파일 이동만으로 업무 LOC 비중이 개선되었다고 재해석하지 않는다.
원래 Backend의 업무 소스 비중 86.9%, HTTP 경로 비중 88.3%는 당시 관측값이며,
현재 분리가 그 도메인 집중을 해결했다는 근거가 아니다.

## 빌드 입력과 캐시: 정적 추론

Before의 COPY . . 다음 솔루션 restore 구조에서는 루트 입력 변경이 10개 이미지의
해당 COPY 이후 계층을 무효화할 수 있다. 10/10은 소스와 Docker 의존성으로 얻은 정적 범위다.
실제 재빌드 시간이나 캐시 적중률을 측정한 값으로 읽으면 안 된다.

After의 각 Dockerfile은 자기 저장소의 SDK/패키지 설정·lock·프로젝트 메타데이터와
고정된 .packages를 먼저 복사한 뒤 선택 프로젝트를 --locked-mode로 restore한다.
그다음 자기 서비스 소스를 복사하고 --no-restore로 publish한다.
따라서 서비스 소스 변경은 해당 이미지의 publish 입력에 영향을 주고,
다른 저장소 Docker context에는 포함되지 않는다. 의존 메타데이터가 그대로라면
restore 계층을 재사용할 수 있는 구조다. 실제 재사용 여부와 시간은 별도 Docker 검증 사항이다.

공유 라이브러리를 수정해도 소비자가 고정 버전을 올리지 않으면 기존 소비자 빌드 입력은
달라지지 않는다. 새 버전 소비 시에는 소비 저장소별로 패키지와 lock을 함께 갱신해야 한다.
호환성 책임이 사라진 것이 아니라 업그레이드를 명시적으로 선택하게 바뀐 것이다.

## 버전 패키지와 검증 경계

Contracts/Foundation 1.0.0의 원본 C# 19개는 바이트 동일성을 별도 manifest로 기록했다.
현재 host의 두 플랫폼 프로젝트 locked restore/build는 부모 검증에서 경고 0·오류 0이다.
첫 sandbox pack에서 NuGet 감사 서버 접속 경고가 있었던 사실과 구분한다.
릴리스 자산 SHA-256은 build/release-manifest.v1.0.0.json이 고정한다.
같은 버전의 다른 바이트를 재발행하지 않으며 패키지는 Git에 넣지 않는다.

Tooling은 Backend/EquipmentConnector 소스 프로젝트를 직접 참조하지 않고,
각각 TestSupport [1.0.0] 패키지로 기존 검증 대상 타입을 사용한다.
이것은 저장소 간 소스 빌드 결합을 제거한 것이며, white-box 내부 타입·Oracle 직접 접근의
검증 결합까지 제거한 것은 아니다. 이후 내부 타입 변경 시 TestSupport 버전도 검토해야 한다.

## 검증 범위와 남은 점

읽기 전용 검사에서는 프로젝트 17개, 다른 저장소 프로젝트 참조 0개,
저장소 밖 명시적 Compile 0개, 내부 패키지 정확 버전을 확인했다.
기본 SDK 소스 포함은 파일 구조 검사이며 MSBuild 전체 평가 결과라고 주장하지 않는다.
서비스별 CI 9개, system CI 1개와 플랫폼 CI/release 2개를 확인했다.
서비스별 CI 파일 존재가 원격 Actions 실행 성공이나 운영 배포 완료를 뜻하지 않는다.

스냅샷 이후 lock/CI 실행 검증은 별도 담당자가 이어서 진행한다.
로컬 캐시에 같은 버전의 임시 패키지가 있으면 lock이 다른 contentHash로 생성될 수 있으므로,
최종 검증은 고정 릴리스 자산과 격리 캐시의 해시 일치를 확인해야 한다.
이 문서는 실제 Docker 시간·전체 회귀 결과를 추정해 채우지 않는다.

플랫폼 NuGet.Config도 저장소별 .nuget/packages 캐시를 사용하고 Git/Docker 입력에서 제외한다.
초기 13:44 해시 대조에서는 22개 잠금 항목 중 19개 불일치를 발견해 각 소유자가 재생성 중이다.
web의 3개 항목은 고정 자산과 일치했다. 아래 후속 검증에서 재생성 후 전체 일치를 확인했다.


## 후속 실측 검증: 구조 추론과 분리한 결과

최종 자산 정리 후 검증 담당자가 생성한 JSON 증거를 다시 읽어 다음을 확인했다.
검증 과정의 개인 경로나 원시 로그는 공개 문서에 복사하지 않았다.

- service-docker-checks.json: 자체 이미지 10개 모두 build 종료 코드 0.
- service-image-inspections.json: 10개 모두 검사용 컨테이너를 시작하지 않고 이미지 파일을 검사.
- service-cache-probe.json: 원본 저장소 밖 임시 복사본에서 문서만 변경하면 restore와 publish
  계층이 모두 재사용되고 이미지 ID도 같았다. 자기 서비스 소스 변경 시 restore는 재사용되고
  publish는 다시 실행되었다. 기존 서비스 이미지 10개의 ID는 바뀌지 않았다.
- service-native-checks.json 및 담당자 검증 보고: 서비스 프로젝트 8개와 독립 테스트 4개를
  새로 복원·빌드하고 테스트 280개 통과. 공통 라이브러리 2개와 Tooling은 경고 0·오류 0.
- service-package-hash-checks.json: 서비스 소유 잠금 항목 17개가 기준 해시와 일치.
  별도 읽기 전용 검사에서도 전체 저장소 Contracts/Foundation 잠금 항목 22개 전부 일치.
- release-package-audit.json: 공개 후보 패키지 4개를 실제 비밀값 집합과 대조한 결과 0건.

캐시 실험은 특정 서비스의 두 종류 변경에 대한 검증이다. 모든 서비스의 모든 변경 패턴을
실험한 것은 아니다. Before의 동일 조건 시간 측정이 없으므로 속도가 몇 배 빨라졌다고
표현하지 않는다. 위 Docker 빌드는 실행 중인 업무 서비스를 교체한 검증도 아니다.

## 검증 중 발견한 두 가지 문제와 수정

첫째, 같은 ID/버전의 임시 패키지가 전역 NuGet 캐시에 먼저 들어가 있었다.
호스트에서 빌드가 성공해도 다른 바이트의 contentHash가 lock에 기록될 수 있었고,
깨끗한 Docker restore에서 불일치가 드러났다. 각 저장소의 패키지 캐시를 격리하고,
고정 릴리스 자산으로 lock을 다시 만든 다음 SHA-512를 비교했다.
최종 읽기 전용 대조에서는 22개 관련 잠금 항목 모두 일치했다.
플랫폼 1.0.0 패키지의 고정 바이트는 변경하지 않았다.

둘째, TestSupport ZIP에는 PDB가 없었지만 DLL의 CodeView 정보에 개인 빌드 경로가 있었다.
PDB 파일을 제외하는 것만으로는 경로 유출을 막지 못했다.
서비스 빌드의 PathMap·결정적 빌드 설정을 보완하고, 공개 전 TestSupport 패키지를 다시
생성해 기준 해시를 재확정했다. 새 공개 후보 4개의 ZIP 및 DLL UTF-8/UTF-16 문자열을
재검사하여 개인 경로·현재 환경 주소·비밀값이 검출되지 않음을 확인했다.
이미 공개한 동일 버전 자산을 교체한 것이 아니라 최초 공개 전 후보를 수정한 것이다.

이 검사는 알려진 비밀값과 경로·토큰 패턴에 대한 검사이며, 모든 형태의 민감정보 부재를
수학적으로 보증하지 않는다. 라이브 런타임 건강 상태·로그인·업무 API 회귀의 최종 완료는
별도 통합 검증 담당자가 확정한다. 여기서는 전체 작업이나 배포 완료를 선언하지 않는다.
